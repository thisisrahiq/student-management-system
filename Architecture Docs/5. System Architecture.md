# 5. System Architecture

## 5.1 Architecture Overview

The Student Management System — Registry Module is built as a full-stack, single-repository web application leveraging **Next.js 14+ (App Router)**, **TypeScript**, **Tailwind CSS + DaisyUI**, **Prisma ORM**, and **PostgreSQL**.

The system adheres strictly to Next.js native backend patterns—utilizing **Server Components** for data fetching, **Server Actions** for data mutations, **Route Handlers** for file streams, and **Zod** for schema validation. No external or secondary backend frameworks (e.g. Express or NestJS) are introduced.

## 5.3 Layered System Breakdown

### 1. Presentation & UI Layer (`src/app/`, `src/components/`)
- **Server Components (RSC)**: Used by default for all page layouts and primary data fetching (`/staff`, `/staff/students`, `/student/results`, etc.). Reduces JavaScript payload sent to the client and optimizes page rendering speed.
- **Client Components (`'use client'`)**: Used selectively for interactive elements like modal popups, dropdown search inputs, file upload forms, and client-side tab switching.
- **Design Token System**: Tailwind CSS utilities combined with DaisyUI components (modals, badges, alert boxes, statistical summary stats, table formats) to present a clean aesthetic.

### 2. Server Action & Business Logic Layer (`src/app/actions/`)
Encapsulates all domain workflows into type-safe asynchronous functions:
- `students.ts`: Handles enrolment, Student ID formatting, searching, filtering.
- `payments.ts`: Handles fee tracking, payment recording, balance computation, overdue state auditing.
- `assessments.ts`: Handles module assessment creation, open/closed evaluation.
- `submissions.ts`: Handles file uploads, timestamp evaluation, late submission detection, resubmissions.
- `results.ts`: Handles grade entry, automatic classification calculation, publish/withhold status toggling.

### 3. Validation & Guardrail Layer (`src/lib/validations.ts`)
- Utilizes `zod` schemas to enforce strict data contracts on both client form submit and server action execution.
- Prevents invalid states such as negative payment amounts, duplicate emails, invalid file MIME types, and out-of-bound grades (<0 or >100).

### 4. Data Access & Persistence Layer (`src/lib/prisma.ts`, `prisma/`)
- **Prisma Client**: Provides type-safe database queries, schema-driven migrations, and transaction management.
- **PostgreSQL Database**: Stores relational tables with strict Foreign Key constraints, Unique indexes, and Cascading deletion rules.
- **Database Seeder (`prisma/seed.ts`)**: Seeds reference data (programmes, modules) and sample operational data (students, payments, submissions, grades) for immediate demo evaluation.

### 5. File System Storage Driver (`public/uploads/`)
- Stores submitted PDF and DOCX documents locally on disk with randomized unique filenames (`UUID_original-filename.pdf`).
- Serves submitted files via standard Next.js static asset routing or custom API stream route handlers.

## 5.4 Technology Stack Matrix

| Layer | Technology | Selection Rationale |
|---|---|---|
| **Framework** | Next.js 14+ (App Router) | Industry standard full-stack React framework with SSR, RSC, and native Server Actions. |
| **Language** | TypeScript | End-to-end type safety shared between database models, server actions, and UI components. |
| **Database** | PostgreSQL | Enterprise-grade relational database satisfying assessment requirement for real persistence. |
| **ORM** | Prisma ORM | Declarative schema definition, type generator, automated migrations, and seed script execution. |
| **Styling** | Tailwind CSS + DaisyUI | Highly customizable utility CSS with pre-built accessible component classes (badges, modals, stats). |
| **Validation** | Zod | Runtime type validation for form inputs, server action parameters, and domain bounds. |
| **Form Handling** | React Hook Form + Zod Resolver | Smooth form state management and error feedback in client components. |
| **Icons** | Lucide React | Clean visual iconography for dashboard metrics, workflow badges, and status alerts. |

## 5.5 Key Design & Architectural Decisions

1. **No External Backend**: All backend functionality resides within Next.js Server Actions and Route Handlers, ensuring single-repository simplicity and straightforward local setup.
2. **Strict Server-Driven Calculation**: Outstanding financial balances, overdue states, late submission flags, and grade classifications are calculated on the server layer to guarantee consistency across Staff and Student views.
3. **Database Transactions**: Financial payments and student enrolment with default fee assignment execute inside Prisma `db.$transaction()` blocks to prevent orphan records or inconsistent state.
4. **Result Confidentiality by Design**: Student queries explicitly filter `WHERE isPublished = true` at the database level. Unreleased grades are never sent over the wire to student clients.
