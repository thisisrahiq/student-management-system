# 1. Assessment Requirements Analysis

## 1.1 Assessment Overview

**Project:** Student Management System — Registry Module  
**Purpose:** Recruitment Technical Assessment  
**Required Stack:** Next.js 14+ (App Router), PostgreSQL, Prisma ORM  
**Time Allowed:** Within 7 working days  
**Submission:** GitHub repository with README  
**AI Usage:** Encouraged, with AI usage documented in the README

The assessment asks for a focused web application covering the four core workflows used by a Registry Administrator:

1. Student Enrolment
2. Fees & Payments
3. Assessment Submission
4. Marksheet & Results

The assessment emphasizes deliberate product decisions, stakeholder understanding, edge-case handling, technical quality, and the ability to explain how AI was used during development.

---

## 1.2 Assessment Objectives

The application should demonstrate that it can:

- Model the core Registry workflows in a real relational database.
- Manage student records and enrolment information.
- Track programme fees, payments, and outstanding balances.
- Manage assessments and student submissions.
- Handle late submissions and permitted resubmissions.
- Record grades and calculate classifications.
- Control when students can see published results.
- Provide separate Staff and Student views.
- Use a real PostgreSQL database through Prisma ORM.
- Provide clean application logic, API/server functionality, validation, and basic error handling.
- Document setup, environment variables, seed data, and AI usage.

## 1.4 Required User Roles

### Staff / Registry Administrator

Staff should be able to:

- Manage student records.
- View and search students.
- Manage programme-related fees.
- Record and review payments.
- Create assessments.
- Review student submissions.
- Enter grades.
- Publish or withhold individual student results.

### Student

Students should be able to:

- View their student information.
- View their assessment-related information.
- Submit assessment files.
- Resubmit before the deadline when permitted.
- View marks/results only after those results have been published.
- View relevant fee/payment information.

Authentication is optional for this assessment. A simple role toggle is explicitly acceptable.

---

## 1.5 Core Workflow Requirements

### Workflow 1 — Student Enrolment

The Registry needs to create and manage student records.

Required student information:

- Full name
- Email
- Date of birth
- Programme
- Academic year
- Enrolment status

Required enrolment statuses:

- Enrolled
- Deferred
- Withdrawn
- Completed

Required functionality:

- Create student record.
- Generate a unique Student ID automatically.
- Search students by:
  - Name
  - Student ID
  - Programme
  - Status
- Filter students by relevant criteria.

Student ID example:

`SMS-2025-0001`

The generated Student ID must be unique.

---

### Workflow 2 — Fees & Payments

The Registry needs to track student financial obligations and payments.

Required functionality:

- Assign a fee amount to each student based on their programme.
- Record payment transactions.
- Store:
  - Payment amount
  - Payment date
  - Payment reference number
- Calculate outstanding balance in real time.
- Identify students with overdue balances.
- Display overdue students on the Registry dashboard.

Core calculation:

`Outstanding Balance = Assigned Fee - Total Payments`

The application should prevent invalid financial states where appropriate.

---

### Workflow 3 — Assessment Submission

Staff create assessments and students submit work against them.

Staff must be able to create an assessment containing:

- Title
- Module
- Submission deadline

Students must be able to:

- View open assessments.
- Upload a PDF or DOCX file.
- Submit work against an assessment.

Submission rules:

- One submission per student per assessment.
- Resubmission is allowed before the deadline.
- Late submissions are accepted.
- Late submissions must be visually flagged.

The application should clearly distinguish:

- On-time submission
- Late submission
- Resubmission

---

### Workflow 4 — Marksheet & Results

Staff enter grades and students can view results only after publication.

Required functionality:

- Staff enter a numeric grade from 0–100 for each student per assessment.
- Automatically apply the required classification.
- Staff can publish or withhold results per student.
- Students cannot see withheld results.
- Students can see their marksheet only after the result has been published.

Classification rules:

| Grade | Classification |
|---:|---|
| 70–100 | Distinction |
| 60–69 | Merit |
| 40–59 | Pass |
| 0–39 | Fail |

## 1.7 Assessment Evaluation Priorities

The assessment has four evaluation dimensions:

| Dimension | Weight | Development Priority |
|---|---:|---|
| Stakeholder understanding | 30% | Very High |
| Feature intuition | 30% | Very High |
| Technical quality | 25% | High |
| AI usage | 15% | Medium/High |

### Stakeholder Understanding — 30%

The data model and UI should reflect realistic Registry operations.

Focus on:

- Logical student records.
- Clear fee/payment relationships.
- Practical assessment workflows.
- Clear result publication states.
- Useful Staff dashboard information.

### Feature Intuition — 30%

Handle reasonable edge cases even when they are not explicitly listed.

Important examples:

- Duplicate student information.
- Invalid payment amounts.
- Payment exceeding the amount owed.
- Missing or invalid assessment files.
- Resubmission rules.
- Late submissions.
- Invalid grades.
- Grade boundary values.
- Withheld results.
- Published results.
- Students with no payments.
- Fully paid students.
- Overdue balances.

### Technical Quality — 25%

Focus on:

- Clean Prisma schema.
- Correct PostgreSQL relationships.
- Working server-side functionality.
- Clear separation of application responsibilities.
- Basic validation.
- Basic error handling.
- Real database persistence.
- Maintainable Next.js architecture.

### AI Usage — 15%

AI may be used freely, but the README must explain:

- Which AI tools were used.
- What they were used for.
- Examples of tasks where AI assisted.
- What was reviewed, tested, or modified manually.
- How the developer retained ownership of the final implementation.

## 1.8 Recommended Non-Functional Requirements

These are implementation considerations derived from the assessment's emphasis on technical quality and feature intuition.

### Data Integrity

- Student IDs must be unique.
- Payment references should be uniquely identifiable where appropriate.
- Grades must remain within 0–100.
- Student-assessment submissions must follow the one-submission/resubmission rules.
- Result visibility must respect publication status.

### Validation

Validate:

- Required student fields.
- Email format.
- Dates.
- Payment amounts.
- Payment references.
- Assessment deadlines.
- File type.
- Grade range.

### Error Handling

Provide meaningful handling for:

- Invalid form submissions.
- Missing records.
- Duplicate records.
- Invalid payments.
- Invalid grades.
- Invalid file uploads.
- Unauthorized workflow actions.
- Database failures.

### User Experience

Provide clear UI states for:

- Loading
- Empty data
- Successful actions
- Validation errors
- Server errors
- Late submissions
- Overdue balances
- Withheld results
- Published results

---

## 1.9 Scope Control

The assessment is **not** asking for a complete Student Management System.

Prioritize the four required workflows:

```text
Student Enrolment
        ↓
Fees & Payments
        ↓
Assessment Submission
        ↓
Marksheet & Results
```

Avoid spending significant development time on unrelated features such as:

- Attendance management
- Timetables
- Full learning management functionality
- Complex payment gateways
- Chat systems
- Advanced notification systems
- Large-scale permission management
- Mobile applications

The objective is to demonstrate how well the required Registry workflows are designed and implemented.
